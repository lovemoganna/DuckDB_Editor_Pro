## 其他已确认问题与修复

1. **计算参数转换丢失**：输入包含 calculation 的聚合、字段、过滤、分组与时间粒度，转换后 calculation 为 undefined；governance 的主体与来源粒度也丢失。现保留这些关系，AI 的 reviewed 状态始终降为 draft。
2. **带 schema 来源引用错误**：`finance.payments` 被拼成 `"finance.payments"`，而不是 `"finance"."payments"`。表结构收集的计数查询现复用公共 `quoteTable`。
3. **正式生成遗漏业务描述**：用户业务描述用于预览，正式生成接口却只接收表和进度回调。复现测试证明正式提示词缺少用户原文。现将同一业务描述传入正式生成，并让预览共用候选转换逻辑。
4. **自动发现的来源 / 依赖含义不清**：原来把来源表写入 dependencies（其契约是字段列表），缺少独立来源和诊断审核标记。现在 sourceTable 保存来源，dependencies 保存 direction / created_at 等实际字段，单位为行，并明确为 diagnostic 草稿。刷新保留已有用户修改，兼容补齐未编辑的历史自动候选。

复现日志：`output/metric-p0-before.log`、`output/metric-p0-proposals-before.log`、`output/metric-p0-context-before.log`。首轮另发现一个测试桩缺少 readQuery 的问题，已补齐测试桩；它没有被登记为产品缺陷。

## 业务价值边界

- 没有找到按 COUNT(*)、direction 或 created_at 自动授予“高价值”状态的明确代码证据，因此不声称已复现该自动评级缺陷。
- 确认存在“核心指标”成功提示及将“可计算、可复用”作为价值说明的表述。已改为候选草稿与诊断用途，避免技术成功被误读为业务价值确认。
- COUNT(*) 合法表示记录数；字段分布和时间分布合法表示数据结构。它们继续可计算、保存和复用，但不能据此宣称业务有效事件、活跃主体、收入或高价值指标。
- 业务复核前需要说明业务问题、应用场景和决策价值，并登记单位、主体、事实粒度、负责人、更新约定、可加性及必要时区。SQL 技术验证与业务审核分别呈现。
- 多表关系仍由完整 SQL 的 JOIN 键、连接类型与预聚合粒度定义；未知关系不靠同名字段猜测。未填写的口径信息明确待确认，不自动补造业务事实。

## 链路验收

| 阶段 | 本次验证 |
| --- | --- |
| 识别 | 原始计数 / direction 分布 / created_at 趋势保留为诊断草稿，真实字段依赖明确 |
| 定义 | 不完整候选可以打开编辑，缺失业务描述可补全，calculation 与 governance 保留 |
| SQL | 分段引用 schema / 表；指标自身来源优先；完整 CTE / JOIN 不替换 FROM；多表未绑定来源明确失败 |
| 计算 | 真正执行 DuckDB；同币种、完成状态、方向维度、月份粒度均参与查询 |
| 验证 | 必须执行当前定义；技术通过不代表业务已审核；既有关闭弹窗 / 过期响应保护回归通过 |
| 保存 | 来源、计算参数、单位、版本与审核状态在保存 / 读取后保留 |
| 复用 | 当前 SQL 用于生成图表；重复生成更新同一图表，预聚合 JOIN 结果保持守恒 |
