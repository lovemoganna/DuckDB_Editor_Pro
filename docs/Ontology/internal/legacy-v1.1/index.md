# 本体建模生产工作流

版本：1.1.0

## 1. 工作流目标

将任意一组业务材料稳定转化为：

1. 可追溯的事实基线；
2. 不依赖实例专名的本体蓝图；
3. 至少一次冻结模型后的盲测验收；
4. 面向指定读者的最终交付物；
5. 可自动验证的运行记录。

流程只负责本体建模及其交付。数据库实现、界面设计、领域外知识和未经确认的业务规则不进入本工作流。

## 2. 运行输入合同

每次运行必须先创建 Run_Manifest.md，并提供：

| 输入 | 必填 | 说明 |
| --- | --- | --- |
| run_id | 是 | 本次运行的唯一标识 |
| workflow_version | 是 | 使用的工作流版本 |
| source_material | 是 | 保留原文，不得预先改写 |
| modeling_scope | 是 | 模型解决什么、不解决什么 |
| acceptance_questions | 是 | 建模前冻结的业务问题 |
| blind_case | 是 | 不向 Step 1、Step 2 暴露的新案例 |
| expected_answers | 是 | 建模前冻结的盲测预期答案 |
| delivery_contract | 是 | 读者、场景、形式和长度 |

输入不完整时不得进入 Step 1。

盲测案例和预期答案必须在 Step 2 开始前锁定。Step 1、Step 2 只能读取各自合同声明的 Manifest 部分，不得读取盲测内容。

## 3. 产物依赖图

~~~mermaid
flowchart LR
  M["Run Manifest"] --> S1["Step 1<br/>事实基线"]
  S1 -->|"G1 PASS"| S2["Step 2<br/>本体蓝图"]
  S2 -->|"冻结模型"| S3["Step 3<br/>盲测验收"]
  S3 -->|"G3 PASS"| S4["Step 4<br/>交付与验收"]
  S4 -->|"G4 PASS"| D["最终交付"]

  S2 -->|"事实或身份问题"| S1
  S3 -->|"模型无法承载"| S2
  S4 -->|"模型失真"| S2
  S4 -->|"交付结构问题"| S4
~~~

下游阶段不得在自己的文档中偷偷修复上游问题。发现问题必须退回拥有该事实或结构的阶段。

## 4. 四阶段合同

| 阶段 | 唯一输入 | 产物 | 质量门禁 | 失败路由 |
| --- | --- | --- | --- | --- |
| Step 1 事实基线 | Manifest 中的原始材料与范围 | Step_1_Fact_Baseline.md | G1：事实、推断、未知完整分层，关键实例和过程有稳定 ID | 输入缺失则停止；身份或事实不清请求补证据 |
| Step 2 本体抽象 | G1 PASS 的事实基线、范围和已冻结的能力问题 | Step_2_Ontology_Design.md | G2：实例映射到稳定类型，能力问题可承载，规则边界明确 | 事实问题退回 Step 1；抽象问题留在 Step 2 |
| Step 3 盲测验收 | 冻结的本体蓝图、盲测案例和预期答案 | Step_3_Reuse_Test.md | G3：每个能力问题都有预期答案、实际答案和 MATCH/MISMATCH | 任一非预期 MISMATCH 都退回 Step 1 或 Step 2 |
| Step 4 交付验收 | G1—G3 PASS 的全部产物与交付合同 | Ontology_Tutorial.md、Step_4_Quality_Report.md | G4：盲测结论可追溯、形式合格、无模型失真 | 模型问题退回 Step 2；表达问题留在 Step 4 |

阶段状态只能是 DRAFT、PASS、RETURN 或 BLOCKED。只有 PASS 产物能成为下一阶段输入。

## 5. 稳定标识

跨阶段引用必须使用以下前缀：

| 前缀 | 含义 |
| --- | --- |
| F / I / U | 事实、推断、未知 |
| INS | 源案例实例 |
| OT / PT | 对象类型、过程类型 |
| RT / ST | 角色类型、状态维度 |
| REL / CON | 关系类型、模型约束 |
| CQ | 能力问题 |
| MAP | 新案例实例映射 |
| GAP | 复用测试发现的模型缺口 |

标识一经进入 PASS 产物，不得重排或复用。删除内容时保留编号并标记 RETIRED。

## 6. 质量优先级

所有阶段统一遵循：

~~~text
事实忠实
→ 身份正确
→ 模型可复用
→ 能力问题可回答
→ 交付可执行
→ 表达简洁
~~~

低优先级目标不得破坏高优先级目标。未知得到准确保留，视为正确结果。

## 7. 标准运行协议

1. 复制 Run_Manifest.md，填写源材料、范围、能力问题、盲测案例、预期答案和交付合同，并将状态设为 DRAFT。
2. 依次执行 Step_1_Prompts.md 至 Step_4_Prompts.md。
3. Step 2 结束后冻结模型；Step 3 才能读取盲测案例和预期答案。
4. Step 3 先生成实际答案，再与预期答案比较，不得为得到 MATCH 修改模型或预期答案。
5. 门禁失败时按失败路由返回，不继续生成下游内容。
6. G1—G4 全部 PASS 后运行 Validate_Workflow.ps1。
7. 验证脚本退出码为 0 后，将 Manifest 状态改为 PASS。
8. 任何上游产物变化，都必须使受影响的下游阶段重新回到 DRAFT。

## 8. 生产完成定义

同时满足以下条件才可交付：

- Manifest 输入完整，工作流版本和运行状态明确；
- G1—G4 全部 PASS；
- 最终结论可通过稳定 ID 追溯到上游产物；
- 冻结模型后，至少一个结构不同的盲测案例完成验收；
- 全部能力问题都有预期答案、实际答案和 MATCH 结果；
- 模型缺口已归类为直接复用、扩展模型或超出范围；
- 最终材料不包含内部审计噪音；
- 自动验证脚本通过；
- 不存在已经失效但仍被引用的产物。
