# Step 2 执行合同：本体抽象

版本：1.1.0

## 输入

只读取：

- G1 PASS 的 Step_1_Fact_Baseline.md；
- Run_Manifest.md 中的 modeling_scope 和 acceptance_questions。

G1 未通过时停止并退回 Step 1。

不得读取 Run_Manifest.md 中的 blind_case 或 expected_answers。完成本阶段并标记 G2 PASS 后，模型版本即冻结。

## 输出

生成 Step_2_Ontology_Design.md，固定包含：

1. 运行标识、阶段状态和模型范围；
2. 建模前已冻结的能力问题；
3. 源实例到类型的映射；
4. 对象类型、过程类型、角色类型、状态维度、关系类型和模型约束；
5. 不含实例专名的最小模式图；
6. 业务规则边界；
7. G2 门禁结果。

## 稳定 ID

| 构件 | ID 前缀 |
| --- | --- |
| 能力问题 | CQ-## |
| 对象类型 | OT-名称 |
| 过程类型 | PT-名称 |
| 角色类型 | RT-名称 |
| 状态维度 | ST-名称 |
| 关系类型 | REL-名称 |
| 模型约束 | CON-## |

所有映射必须引用 Step 1 的 INS、F、I 或 U 标识。

## 抽象规则

- 类型定义不得依赖实例专名；
- 状态描述“同一对象此刻怎样”，不得创建新对象；
- 角色必须绑定过程，不得替代对象类型；
- 关系名称必须表达具体语义；
- actualPrecedes 不得自动升级为 requiresCompletionOf；
- 一次事件只产生候选结构，不产生普遍业务规则；
- 每个模型构件必须服务至少一个 CQ。
- 不得为了尚未读取的盲测案例预留构件。

## G2 门禁

只有同时满足以下条件才能标记 PASS：

- 所有关键实例都有类型归属或明确未建模原因；
- 删除实例专名后，模式仍然成立；
- 每个 CQ 都有构件承载；
- 事实、规则、候选规则和未知分开；
- 模式图与构件表一致；
- 没有上游事实问题。

发现事实或身份问题时标记 RETURN 并退回 Step 1。抽象问题留在本阶段修正。

## 禁止

- 不新增源材料事实；
- 不写数据库字段或界面实现；
- 不为追求完整引入与 CQ 无关的构件；
- 不生成培训文章。
